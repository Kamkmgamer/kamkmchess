# AI conditional pre-moves

## Context

Today only the *human* can pre-move (one Chessground premove while the AI thinks). The AI seats — API models, page agents (WebMCP), and remote MCP agents on the Go server — must think through every turn, even when their reply is forced (opening theory, recaptures, forced sequences). We let an AI attach **conditional pre-moves** to its move: "I play e4; if the opponent replies e5 or Nc6, play Nf3 automatically" — optionally chained deeper ("…and if it then plays Nf6, play Bc4"). The AI chooses how many moves to pre-move (none, one rule, or a small tree).

Decisions (no user answers came back, so using the recommended options):
- **Surfaces**: local play screen (API models + page agents) **and** hosted MCP games (Go server). Online friend matches stay out of scope (they disable even human premoves).
- **Depth**: nested sequences, capped at 3 pre-moved replies deep, ≤ 8 branches per level.
- **Visibility**: the human sees a notice ("AI will play Nf3 if you reply e5") like the existing human premove notice.
- **Engine seats (Stockfish) don't premove** — they search fresh each turn; a cached move is strictly worse. Only LLM-driven seats arm premoves.
- **Illegal premove at fire time is discarded silently** (no budget penalty) — same precedent as Chessground's `playPremove` ("invalid queues are discarded"). The position that made it illegal may be one the AI didn't anticipate.
- Premoves are **consumed on the opponent's move**: the matching branch fires (its nested tree re-arms at the new position), all other branches are discarded (they were keyed to a position that no longer exists). Undo/takeback restores the armed tree with the baseline checkpoint, so it re-arms correctly.

## Protocol shape

A model reply gains an optional `premoves` array (JSON object replies and the `make_move` tools). `then` is either a coordinate move or a nested object:

```json
{"move":"e2e4","plan":"...",
 "premoves":[
   {"on":["e7e5","b8c6"],"then":"g1f3"},
   {"on":["c7c5"],"then":{"move":"c2c3","premoves":[{"on":["g8f6"],"then":{"move":"d2d4"}}]}}]}
```

- `on` entries and `then` moves are coordinate form (`e2e4`, promotions appended). Castling triggers are normalized to the king-landing form (reuse `castlingSide`/`kingCastlesTo` from `src/rules/transitions.ts`, same normalization `applyCoordinateMove` does).
- Reply legality is checked at **fire time** (per-branch SAN is computed at arm time for the notice; branches whose reply is illegal in that hypothetical position are kept but will simply be discarded if reached).
- Malformed `premoves` never blocks the move: the move still plays, the raw value is kept in retained fields/archive for audit.

2. **Fire**: extend `ControllerMoveEventV1.kind` with `'premove'` (a model-side move fired from armed conditions — skips the `activeRequest` check that `acceptMove` requires for `'model-move'`, src/controller/index.ts:2800). After `acceptMove` commits any move (human or model), check the *opponent* side's armed extension: if the just-played move matches a trigger (with castling normalization), internally chain `this.acceptMove({kind:'premove', fence: createFence(newCheckpoint), move: reply})` — same internal-chaining precedent as `applyModelTurnEffect` → `acceptMove` (line 2103). The fire consumes the tree; the fired branch's nested tree re-arms. Archive the fired move as `'model-move-accepted'` with `premove: true` in the event details. Game end stops the chain (acceptMove already handles terminal positions; guard recursion with the depth cap).
3. **Snapshot**: add `premoves: ArmedPremovesSnapshotV1 | null` to `ControllerSnapshotV1`, derived from the extension in `snapshot()`, with per-branch display SAN (computed at arm time by applying trigger → reply with `applyCoordinateMove`) so the UI shows "if e5 → Nf3" without re-searching.
4. Clear the extension on `initialize` (fresh checkpoints have no key), on game end, and when the game is restored into a finished/recovery state. Undo works via the existing undo-baseline snapshot restore.

## Part D — hosted MCP server (Go)

1. **`backend/mcpserver/game.go`**: `make_move` gains `premoves` arg. Parse/validate shape + caps **before** executing the move (like the `coordinateMove` regex check; bad shape → `errTool`, not an illegal attempt). `then` nests like the TS format.
2. **Storage**: an in-memory per-match registry on the `Server` (mutex-guarded `map[matchID+seat]armedTree`), lifetime like `sess.plan` but keyed by match so a `resume_game` reconnect keeps it; cleared when the match is observed finished and consumed on fire. Documented limitation: lost on server restart.
3. **Fire**: a `maybeFireArmedPremoves(ctx, sess)` helper called from the `waitForTurn` poll loop (game.go:625 — after `GetMatch`, when it's the agent's turn and the last move matches a trigger) and from `get_board`. It submits the reply via the same `ActionSubmitMove` command path (`s.command(sess, match, lease, ...)`); an illegal reply is dropped. After firing, `waitForTurn` keeps waiting for the *next* reply within the original bound, so `make_move(wait)` returns once the opponent has answered the premove too.
4. **Watch payload** (`backend/mcpserver/links.go` watch handler): include the agent's armed tree (with display SAN) so the human's hosted board can show the notice; `src/agents/hosted-session.ts` maps it into the snapshot's `premoves` field.
5. Update the hosted tool schema + `instructions` text (game.go:152-195).

## Out of scope

- Online friend matches / browser agent seats via the online command protocol (`online-workspace.tsx` premoves stay disabled).
- Stockfish/browser-engine seats arming premoves.
- Durable (DB) storage of armed premoves on the hosted server.
