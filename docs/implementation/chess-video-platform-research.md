# Browser chess video platform research

Checked 2026-11-01 by fetching first-party specifications, documentation, and source over HTTP. This note covers platform facts and proposed policy for a browser-only, no-LLM recap. It does not establish what this site's running browser has cached or which codecs its device can encode.

The documented APIs permit a generated canvas timeline and synthesized soundtrack to become an MP4 or WebM entirely in the browser. WebCodecs plus a muxer provides explicit media timestamps. Canvas capture plus MediaRecorder provides a recording fallback. Availability, speed, output playback, and background behavior require runtime checks.

## Checked facts

### WebCodecs and capability checks

- `VideoEncoder` and `AudioEncoder` are separate interfaces. Both have `[Exposed=(Window,DedicatedWorker), SecureContext]`. Each has its own `isConfigSupported`, `configure`, `encode`, `flush`, `close`, output callback, and error callback. Finding `VideoEncoder` does not establish audio encoding support. The specification does not require support for "any particular codec type or configuration." Check the actual video codec, dimensions, bitrate, and frame rate, and the actual audio codec, channel count, sample rate, and bitrate. [W1]
- `isConfigSupported` returns a supported flag and the recognized configuration. Unrecognized dictionary members can be ignored. A supported configuration is a capability result, not a completed export or a resource reservation. Configure and encode failures still need handling. [W1]
- Presentation timestamps use integer microseconds. Their origin "does not necessarily correspond to wall-clock time." A generated video can therefore use frame-index timestamps instead of waiting for playback time. The API emits encoded chunks and codec metadata, including `decoderConfig`; it does not itself write an MP4 or WebM file. A muxer must receive the encoded packets and needed metadata. [W1]
- `encodeQueueSize` counts pending encode requests, and `dequeue` reports decreases. `flush` completes queued work and emits pending output. `close` aborts pending work and releases resources. `VideoFrame` and `AudioData` also have explicit resource lifetimes. Batch export needs backpressure and prompt resource release. [W1]
- The current resource-reclamation section permits reclaiming inactive codecs with `QuotaExceededError`, but explicitly protects active background encoders. It says this "prevents long running encode tasks from being interrupted." This is a specification rule, not evidence that every deployed browser implements the current text or that the page cannot freeze or be discarded. A worker alone does not guarantee background completion. [W2, B2]
- Secure-context requirements are distinct from cross-origin isolation. HTTPS and potentially trustworthy local origins are defined by the Secure Contexts specification. Check `isSecureContext` at runtime. WebCodecs does not require `crossOriginIsolated` in its interface declarations. [W1, S1]

### Mediabunny muxing and generated media

Checked repository snapshot `cd6612380c7e3f1261d74b9b550e6fc3b65a53bc`, whose `package.json` reports version `1.65.0`. This is a researched candidate, not an installed dependency or a verified npm release. [M0]

- The first-party docs describe `Output`, `Mp4OutputFormat`, and `WebMOutputFormat`. They distinguish container support from codec availability: "The availability of the codecs provided by the WebCodecs API depends on the browser and thus cannot be guaranteed by this library." `canEncodeVideo` and `canEncodeAudio` accept concrete encoding settings. The simpler `canEncode` uses example settings, so it is insufficient for a different export configuration. [M1, M2]
- `CanvasSource.add(timestamp, duration)` accepts a repeatedly updated canvas. These library arguments use seconds, unlike WebCodecs' microseconds. `AudioBufferSource` accepts Web Audio `AudioBuffer` instances and appends successive buffers. `AudioSampleSource` allows explicit audio samples. Await each source's `add` promise to respect backpressure, then close completed sources and finalize the output. `cancel` is also documented. [M3, M4]
- `BufferTarget` holds the whole output in a contiguous, growing `ArrayBuffer`. Its docs warn that a large output can crash the page through memory exhaustion. `StreamTarget` writes chunks with byte positions and propagates writable-stream backpressure. A destination must honor those positions; blindly concatenating chunks is wrong when a container rewrites earlier bytes. `FileSystemWritableFileStream` is a documented destination. [M4]
- A streaming target does not remove all buffering. The muxer needs packets from all tracks in timestamp order. Its docs warn that encoding all video before audio can hold all video packets in memory. Interleave tracks, or send the smaller audio track first and close that source. [M4]
- MP4 `fastStart: 'in-memory'` keeps media chunks until finalization. `false` places metadata at the end and uses less memory. `'reserve'` needs a maximum packet count. `'fragmented'` permits append-only output with shorter buffering, but the docs warn about playback and seeking compatibility. The default behaves like `'in-memory'` with `BufferTarget` and `false` with other targets. WebM's `appendOnly` option also affects duration and seeking. Streaming storage and shareable-file layout are separate choices. [M2]
- The core package is MPL-2.0, confirmed in both `package.json` and `LICENSE`. Sections 3.1, 3.2, and 3.4 require the covered source, source-access information, and license notices when distributing covered executable code. Section 3.3 permits a larger work under other terms while retaining those obligations. Budget a source/license notice for a bundled copy and any modifications. Do not describe the current core as MIT licensed. [M0, M5]

### Offline soundtrack rendering

- `OfflineAudioContext` renders an audio graph without audio hardware. The spec says it "renders as quickly as possible" and resolves with an `AudioBuffer`. Schedule oscillators, gain envelopes, filters, and any owned samples against audio time, then call `startRendering`. The render can be faster than real time; no speed is promised. The ordinary full-render path produces the whole PCM buffer. [A1]
- `AudioBuffer` channels contain 32-bit floating-point PCM. Derived storage for 60 seconds of stereo at 48 kHz is `60 * 48000 * 2 * 4 = 23,040,000` bytes, about 22 MiB, before copies and encoding. Offline rendering does not make audio memory free. [A2]
- A live `AudioContext` can route synthesized audio to `MediaStreamAudioDestinationNode`, whose stream can accompany canvas video in MediaRecorder. This requires no microphone capture. An `AudioContext` may remain suspended until the browser allows it to start, including an activation requirement. Offline rendering does not imply that live playback or recording audio has started. [A3]

### Canvas and MediaRecorder fallback

- `HTMLCanvasElement.captureStream` produces a video track from canvas painting. `captureStream(0)` plus `requestFrame` gives manual capture requests, but the API supplies no per-frame presentation timestamp. The spec requires a paint with new content before adding the frame. This is a live MediaStream recording route, not a specified faster-than-real-time batch renderer. Manual frame requests do not turn MediaRecorder into WebCodecs. [R1, R2]
- The canvas must be origin-clean. Otherwise capture throws `SecurityError`; later tainting mutes the captured track. Piece images, fonts, and other drawn assets need valid origin/CORS handling. [R1]
- `MediaRecorder.isTypeSupported` checks a container/codec MIME combination. The spec warns, "Recording may still fail if sufficient resources are not available." Probe MP4 and WebM candidates with both video and audio codecs, then inspect the actual recording MIME type and handle construction/start/error failures. [R2]
- `timeslice` specifies a minimum amount of collected media before a data event, subject to a larger browser minimum and task scheduling. It is not an exact clock or memory ceiling. Individual blobs "need not be playable"; the combination from a completed recording must be. Keeping every emitted blob still retains the whole export. Large timeslices can also exhaust resources. [R2]
- Chrome's first-party timer documentation says `requestAnimationFrame` waits for page visibility and documents throttling of hidden-page timers. Its lifecycle documentation says frozen pages suspend freezable tasks and pages can be discarded. These are concrete reasons a live fallback cannot promise correct pacing in a hidden tab, on a locked phone, or after suspension. Audible audio is not a general immunity from lifecycle intervention. The Chrome article's numeric throttling thresholds are not a cross-browser contract. [B1, B2]

### Storage and this site's engine cache

- Service Worker Cache Storage and the browser HTTP cache are separate. The specification states, "Caches are not shared across origins, and they are completely isolated from the browser's HTTP cache." A `caches.match` miss does not prove an HTTP-cache miss. Another site's cached Stockfish does not establish availability in this site's storage context. [S2]
- This site can inspect its own managed cache entries and loaded engine state. The checked cache APIs expose this site's storage context, not a desktop-engine inventory. A complete, versioned set of this site's engine assets is stronger evidence than a remembered "downloaded" flag. The last sentence is an implementation inference from the storage model, not a cache durability guarantee. [S2, S3]
- Storage `estimate` reports usage and quota estimates. Storage pressure can clear nonpersistent data; persistence requests may be denied. Neither a storage estimate nor persistence reserves RAM or guarantees an export will finish. [S3]
- `navigator.storage.getDirectory` accesses the origin's bucket file system without a user file-picker prompt. File handles and writable streams are secure-context interfaces. An origin-private temporary file can avoid holding all encoded bytes in JavaScript memory if the muxer writes directly to it. Quota errors and temporary-file cleanup still need handling. [S4]
- `showSaveFilePicker` is a separate optional API with secure-context and activation requirements. Obtain the handle during a user gesture, or offer a later Save action. Do not assume it remains callable after lengthy analysis and rendering. Check the API before selecting this destination. [S5]

### Stockfish 19 and UCI grading

Checked the official `sf_19` tag at commit `edb0d9db6731067ec50ce619ff372b463bc4dd5d`, current official command docs, and the Stockfish.js maintainer's repository at `10b49d8bb4539a0743013772ed735a63853a3b05`. The latter reports npm package version `19.0.1`; this does not establish the running site's engine identity. [F1, F2]

- Stockfish.js documents full and Lite builds, each with threaded and single-threaded variants. Its full build is approximately 94 MB and Lite single-threaded approximately 1.7 MB. Threaded builds require cross-origin isolation and `SharedArrayBuffer`; single-threaded builds do not require those headers. The maintainer attributes Lite's smaller size to a smaller neural network. Engine/package code is GPL-3.0; non-engine code has separate MIT terms. [F2]
- UCI `MultiPV` means "Output the N best lines". It is not the number of plies and does not guarantee the played move appears. Stockfish 19 numbers `multipv` from one and limits output to available root moves. Lower skill settings can internally enable additional MultiPV search and select weaker moves. [F1, F3]
- `go ... searchmoves <moves>` restricts root moves. The `sf_19` parser consumes the rest of that line as moves, so put `searchmoves` last. Its root-move construction falls back to all legal moves if no valid supplied root move remains. Validate the played move before using this command. [F1, F4]
- Scores and WDL refer to the root side to move. Comparing analyses before and after a move requires changing perspective: negate a numeric score and exchange W/L when changing sides. Comparing unrestricted and played-move-restricted searches from the same root avoids that sign change. The root-score construction and WDL calculation are visible in the official source; the evaluation trace explicitly converts side-to-move values to White's perspective. [F3, F5, F7]
- Ordinary `score cp` is normalized evaluation, not literal material. `sf_19` computes it from a material-dependent WDL model. `score mate` is a separate signed distance in moves and must remain a separate type. Terminal mate zero needs the actual board/result context. Stockfish's formatter also represents tablebase scores specially. [F5, F6]
- With `UCI_ShowWDL`, output is wins, draws, losses per thousand, with the three values summing to 1000 in the source. The official docs call these "approximate WDL statistics" for engine self-play at fishtest LTC conditions. They are not measured human win probabilities. The docs mention game ply; the pinned `sf_19` implementation instead parameterizes this model by material. Use the selected engine's output rather than reconstructing a supposedly universal cp-to-WDL formula. [F1, F5]
- Search output includes `depth`, `multipv`, PV, and optional `lowerbound` or `upperbound`. A bound is not an exact search value; an unflagged value is still an engine estimate. MultiPV output can reuse a previous iteration's score and depth. Keep those fields together rather than combining unrelated lines. [F3]
- `isready` returns `readyok` even while a search continues. It is not a search-completion barrier. Use `bestmove` to finish a search, including after `stop`, before starting the next job. Preserve move history with `position ... moves ...` for repetition detection. Stockfish 19 can terminate on invalid positions or illegal moves. Its source can emit `bestmove (none)` for terminal positions. [F1, F3, F5]

## Proposed policy, not checked platform guarantees

- Prefer a deterministic canvas timeline, offline music, and WebCodecs with Mediabunny. Probe MP4 with AVC/H.264 and AAC first, then WebM with VP9 or VP8 and Opus. Check both codecs at the chosen settings and verify a short finalized file with audio before committing to a full export. No browser/version allowlist replaces those checks. An AAC WASM extension is an additional package, not a capability supplied by the core library; it is outside this recommendation.
- Use full Stockfish 19 only when this site already has a usable loaded instance or a verified complete set of its pinned cached assets. Otherwise use its Lite build. Do not fetch the large full build merely to test availability. A browser's HTTP cache is not a reliable general inventory; base this rule on this site's explicit cache/engine contract. Keep analysis at full strength independently of the opponent difficulty setting.
- Grade a move by comparing an unrestricted root search with a search restricted to the played legal move, under the same declared budget and engine build. Reuse a matching MultiPV result only when the played move and quality requirements match. Expected score `E = (W + D / 2) / 1000` and loss `max(0, E_best - E_played)` are possible heuristics. Grade thresholds, highlight selection, and terms such as "brilliant" are product rules, not UCI facts. Handle mate, terminal draws, and bound-only results separately.
- Schedule the music from the same recap timeline, with a fixed seed and authored notes, envelopes, fades, and event accents. Keep original composition or asset licensing explicit. Use a short soundtrack or bounded chunks if PCM size becomes material. No narration or model call is needed.
- Keep only a small number of raw frames in flight. Await encoder/muxer backpressure, interleave tracks, and release frames, samples, encoders, streams, and temporary files on completion or cancellation. Estimate encoded size from duration and requested bitrate, but do not present that estimate as a hard bound. A direct file target or origin-private temporary file helps larger exports; a final in-memory `Blob` can restore the memory cost.
- Use a live, real-time canvas/MediaRecorder fallback only after its combined audio/video MIME probe succeeds. Require a visible tab during recording and handle visibility loss explicitly. Do not advertise uninterrupted background or locked-screen export for either path before testing target devices. When no tested audio/video route works, report that limitation rather than silently exporting a music-free file.
