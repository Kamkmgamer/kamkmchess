## The design in one paragraph

One acceptance of one invitation is **one transaction**. The invitation row is
locked, the acceptance is recorded, the canonical match is written through the
shared allocation seam of `backend/online` and the guest seat credential is
minted, and all four commit together. A crash can therefore never leave a
spent invitation without a game, and no reconciler has to look for an
orphaned acceptance. The evaluator that validates the starting position runs
**outside** that transaction, so no rules call is ever made while a row lock
is held, and every read of the transaction runs on the transaction itself, so
a loser of a contended acceptance never waits for a second connection of the
pool while it holds the lock of the invitation.

A rematch is the same shape. The offer, the new match and the credential of
the accepter commit together, so a crash leaves the offer `pending` for the
opponent instead of stranding it in a durable reservation. The rematch
reverses the colors, retains the setup and names the new match after the
offer, so a retry always names the same game.

The effective status of an invitation is read from its deadline. An
invitation whose twelve hour deadline passed reads as `expired` even though
no sweep ever wrote that state, and the refused acceptance answers `410`
with its own code, so the browser can tell the invitee that the link expired
instead of reporting a generic conflict.

### F-1 (P1) — the acceptance key is not bound to a guest acceptor — **not implemented, by decision, with a documented contract**

The finding is correct as a description of the code: a guest acceptor has no
identity, so the acceptance key is the whole capability of that acceptance and
whoever holds it can resume the acceptance and rotate the credential of the
seat.

It is **not** implemented, because:

* the acceptance key is a bearer secret of one accept intent by design. It is
  24 random bytes (192 bits) from `crypto.getRandomValues`, it is stored only
  as a SHA-256 hash, the service never returns it and it never enters a log
  line. The public acceptance identifier is never enough to resume an
  acceptance;
* an anonymous lost answer cannot prove that the credential was never
  received. Requiring the *current* credential of the seat would make the
  recovery of a lost answer impossible, which is the opposite of the contract
  requirement;
* binding the key to the guest identity would not bind the caller: the guest
  identity is generated by the server, so `sha256(key || guestID)` is a
  function of the key alone. It would add a stored value and no security.

What was done instead:

* the **entropy** of the key was hardened. The default source of
  `createAcceptanceKey` now encodes the 24 random bytes without loss (one
  byte becomes two characters of a sixteen character alphabet, so two byte
  sequences never produce the same text) and **fails closed** when the
  environment has no secure random source, instead of falling back to
  `Math.random`. The service side accepts the shape and stores only the hash
  (`TestTheAcceptanceKeyIsStoredOnlyAsAHash`);
* the **security contract** is now written down in the module doc of
  `backend/invite`, in the comment of `backend/migrations/0010_friend_invitations.sql`
  and in `docs/online/matching-interfaces.md`: the key is the resume
  capability of a guest acceptance, it stays secret, and the account path is
  bound to the account.

Residual, recorded honestly: a caller that knows the acceptance key of a
guest acceptance can rotate the credential of that seat. The blast radius is
the origin scope of the credential and the entropy of the key. The rotation
is also now inside the acceptance transaction, so the seat never carries two
usable secrets at once.

### F-2 (P1) — a guest rematch accepter that lost the answer is locked out — **implemented**

`AcceptRematch` honours `RotateCredential` on the duplicate path, and it
mints a fresh credential of the new seat whenever the caller cannot use the
credential it holds. The service learns that from the credential the caller
presented: a rematch is a new match, so a credential of the finished match
cannot authorize the new seat. The HTTP route forwards the binding of the
presented credential, and the answer of the retry therefore carries the
credential of the new match and the live view of the new game again.

* `TestPostgresFriendGuestRematchLostAnswerRecoversTheCredential`
* `TestPostgresFriendGuestRematchRetryAnswersTheLiveView`

A routine retry never supersedes a credential the caller already holds: a
caller that presents the credential of the **new** match keeps it.

### F-3 (P1) — the consumption and the creation of the match are two transactions — **implemented**

The claim and the completion are one transaction now. The consumption of the
invitation, the acceptance row, the canonical match and the guest seat
credential commit together, and the evaluator validation stays outside the
transaction. The promised acceptance reconciler is therefore **not** needed,
and the comment of the migration that promised it was corrected. The
regression blocks the creation of the match with a second connection, cancels
the acceptance and shows that the invitation is still open, that no
acceptance was recorded and that no match exists, and that the same key
accepts the invitation afterwards.

* `TestPostgresFriendAcceptanceCommitsTheMatchAndTheCredentialTogether`

### F-4 (P2) — the expiry of an invitation is never recorded — **implemented**

The status of an invitation is the effective status: an open invitation whose
deadline passed reads as `expired`. The preview reports it and the refused
acceptance answers `410` with the code `expired`, so the browser can tell an
expired link from a spent one. The expired state of the schema, of the Go
enum and of the browser parser is therefore no longer dead.

* `TestPostgresFriendExpiredInvitationReportsItsState`

### F-5 (P2) — a crashed rematch reservation strands the offer — **implemented**

The reservation and the creation of the match are one transaction now, so a
crash cannot leave a durable `accepting` reservation: the offer stays
`pending` and the opponent can accept it. The one-winner property is kept:
the offer row is locked for update, the update to `accepted` names the
accepter, and a superseding proposal or a second acceptance observes the
committed state.

* `TestPostgresFriendRematchAcceptanceCommitsTheOfferAndTheMatchTogether`
* `TestPostgresFriendConcurrentRematchAcceptanceCreatesOneMatch`

The durable `accepting` state is no longer written. The wire type keeps the
value, because the browser may still read it from an offer of an older
build.

### F-6 (P2) — a guest inviter can accept its own invitation — **partially implemented, with an explicit limit**

The server refuses an acceptance whose acceptor is the same participant as
the inviter, and it does so **before** the invitation is consumed: the
refusal now happens inside the acceptance transaction, so a refused self
acceptance spends nothing.

The rest of the finding is **not** implemented, and no sybil defence is
claimed. An anonymous guest inviter is a fresh opaque identity and the
service never tracks people, so the server cannot tell that the same human
opens the link it created. The browser can avoid the case itself, because it
knows which links it created: `isLocallyOwnedInvitation` is the rule of the
interface for that. It is a convenience, not an identity proof, and it is no
substitute for the consent of the other player.

* `TestPostgresFriendSelfAcceptanceIsRefusedBeforeConsumption` (shipped)
* `isLocallyOwnedInvitation` in `src/online/friends.ts`

### F-7 (P3) — the accept route tells a stranger that a named challenge exists — **implemented**

An acceptance of a named challenge by a caller that is not the named account
answers exactly like an unknown invitation: `404` with the code `not_found`.
The error mapping of the surface and its comment now describe the real
behaviour.

* `TestPostgresFriendNamedChallengeIsInvisibleToAStranger`
* the shipped test `TestPostgresFriendInvitationLinkAndChallengePaths` now
  expects the same refusal for the preview and for the acceptance

### B-09 (P1, `backend-review-r2.md`) — the public preview published the raw routing identity — **implemented**

A declared model label is a private routing identity until its owner chooses
a public label for it, and the preview of a link is unauthenticated. The
invitation path stored the declared label verbatim and published it in the
`inviterControl` field of the preview.

The declared control of the inviter and of the acceptor is now resolved
**before** it is stored, with the canonical resolution of the service
(`online_resolve_public_model_label`). The resolution is the single source of
that policy, so the friend module owns no second copy of it: a known public
model name and a public label the owner registered for their own account are
kept, and every other declared label becomes the neutral label. The stored
invitation, the stored acceptance, the stored seats, the creation answer, the
preview, the acceptance answer and the rematch answers therefore carry the
publishable label only.

* `TestPostgresFriendNeverPublishesAPrivateRoutingIdentity` (the private
  label appears in none of the answers, in neither stored row and in neither
  seat of the created match)
* `TestPostgresFriendKeepsARegisteredPublicModelLabel` (a registered public
  label and a known public model name are kept, the label of another owner is
  not, and the engine constant of the shared policy is intact)

The human and the no-model validation of a control is unchanged, and the
friend surface still offers no built-in engine seat, so the engine constant
never appears in a friend answer.

The two remaining `[CONFIRMED]` lines of R5 and R6 are the dispositions of
the owner, not open defects of this branch: the server cannot tell that an
anonymous guest who created a link is the same human who opens it, and the
acceptance key of a guest acceptance is the whole capability of that
acceptance by design. The full log of the run is kept next to the review
report of the round.

R1 is the same decision. The retry of a guest acceptance **without** the
rotation answers `403`, because the caller presents no credential of the
match and the live view is membership gated. Handing that live view to an
anonymous caller that only knows the acceptance key would turn the key into a
seat credential, which is the trade of F-1 that the owner declined. The
browser asks for the rotation when it holds no working credential
(`needsCredentialRotation`), and the retry with the rotation answers `200`
with the credential and the live view.

## The removal of a participant

The privacy worker sanitizes the auxiliary rows of a removed participant, and
it does it **account first**: the removal takes the account scope lock of the
removed subject and then the row locks of the rows it sanitizes. A friend
write that names a participant therefore has to take the same account scope
lock **before** its own row lock, or the two flows invert and deadlock.

The friend service now follows the canonical protocol of `backend/locks` and
the shared reference of `backend/subject`:

| Write | Scopes it locks | Recheck |
| --- | --- | --- |
| the creation of an invitation | the inviter, the named recipient of a challenge | the inviter, the recipient |
| the acceptance of an invitation | the inviter, the acceptor | the inviter, the acceptor |
| the **cancellation** of an invitation | the inviter | the inviter |
| the proposal of a rematch | the two participants of the finished match | the two participants |
| the acceptance of a rematch | the two participants of the finished match, the proposer of the offer | the two participants, the proposer |
| the credential recovery of an invitation or of a rematch | the owner of the seat | the owner of the seat |

The scope locks are taken before the row lock of the invitation or of the
rematch offer, and the durable removal of every participant is rechecked after
the locks and before the row is written. The check names a participant by its
one-way reference, so the removal tables are read without the raw identifier
of a removed subject, and the guest path keeps its bearer capability: an
anonymous guest is a fresh identity that no removal names.

The recheck has three parts, and each of them closes a hole of its own:

* a participant that carries the **anonymized sentinel** is a removed
  participant. The privacy sanitation replaces the identifier of a removed
  subject with that constant, so a row that carries it names nobody any more.
  Without this part the fence was blind: it locked the scope of
  `"anonymized"` and asked the removal tables about `"anonymized"`, and no
  removal ever names that string, so the check always passed;
* a participant whose account or of whose guest seat a removal was recorded is
  named by the durable removal records, compared through the one-way
  reference of the subject;
* a participant whose **own** one-way reference **and kind** is named by a row
  of the **removal ledger** of that match was removed from that match. The
  ledger is the match scoped record of a removal, so it answers the question
  even when the seat row of an older backup still names the removed subject,
  and it is the record that survives a restore of an older backup. The check
  is **participant scoped**: the removal of the opponent of a match does not
  take the seat of the survivor away, and the game stays live. The kind is
  part of the check, because an account and a guest that share an identifier
  share their one-way reference as well.

The new refusal is `invite.ErrRemoved`, and the HTTP surface answers it with
`403` and the code `not_authorized`, so the error vocabulary of the surface
does not change.

The write names the participants it really writes for. A fresh acceptance
creates the match of the inviter and the acceptor, so both are rechecked. A
**resumed** acceptance creates nothing and writes no row of the inviter, so
only the acceptor is rechecked, and the removal of the inviter does not take
the seat of the acceptor away. The credential of a seat is recovered for the
owner of that seat alone.

A resumed acceptance may present **no identity at all**: the acceptance key is
the whole capability of a guest acceptance. The scope of the stored acceptor is
locked before the row of the invitation in that case as well, so an anonymous
resume is ordered against the removal of that acceptor. The read that learns
the stored acceptor takes no row lock, so the order of the locks is unchanged.

The identity of a resumed acceptance is compared **exactly**: the kind is part
of it, because the one-way reference of a subject does not carry the kind. An
account and a guest that share an identifier are two different participants,
and the account never resumes the acceptance of the guest. A request that
presents no identity resumes the acceptance of the key, which is the bearer
capability of that acceptance.

A retry can meet an acceptance that another request is writing right now: the
acceptance of the key is read before the locks, so the retry misses a row that
is not committed yet. The retry waits for the row of the invitation, the first
request commits, and the authoritative lookup finds the acceptance whose
acceptor was never locked. The write is **rolled back and started again** in
that case, so the scope of the stored acceptor is always taken before the row
of the invitation and never after it: no scope lock is ever taken after a row
lock, so the order of the removal is never inverted.

An offer that can never be accepted any more is not published. The pending
read is a **projection**: it never writes, so a `GET` never changes the
personal row of a removed participant, and it never raises a database error
for an offer of an older build.

## Known limitations

1. The friend client is not composed into the application yet. That is the
   work of the workspace worker; this ticket owns the typed client only.
2. A guest that lost the answer of an **invitation** acceptance still has to
   ask for the replacement explicitly with `rotateCredential`, because the
   service cannot tell a caller that holds no credential from one that holds
   a working one. The rematch path does not need the flag, because the
   credential of the finished match cannot authorize the new seat.
3. A guest whose seat credential of the finished match expired cannot accept
   a rematch, because the acceptance of a rematch needs a credential of the
   finished match. The lifetime of a guest credential is a separate decision
   of the authorization surface.
4. The service does not run the browser agent and does not publish a
   spectator view. The friend surface creates the canonical match and hands
   the seat over.
5. The `accepting` state of a rematch offer is no longer written. The value
   stays in the schema, in the Go enum and in the browser parser, because an
   offer of an older build can still carry it.
6. Two **concurrent** duplicate acceptances of one rematch by the same guest
   can supersede each other: the second answer holds the live credential and
   the first one is superseded. The browser therefore has to use the last
   answer of its own accept intent. The same race exists on the invitation
   path, where the browser asks for the replacement explicitly.
7. The durable removal fence of the foundation worker is not part of this
   ticket. The friend acceptance calls the shared allocation seam
   **inside** its own transaction (`CreateMatchInTx`), so the in-transaction
   gate of the foundation covers the friend path as well, as long as the gate
   sits inside `createMatchInTx` and not only inside `CreateAllocatedMatch`.
   The foundation worker owns that file; this ticket does not touch it.
8. The refusal of a removed participant is conservative. A resumed
   acceptance whose invitation names a removed participant is refused as
   well, even though the recovery itself would not write the identifier of the
   removed subject again. The refusal is the fail closed answer, and the
   privacy sanitation of that invitation would break the recovery anyway.
9. The **canonical writer** of the service (`requireParticipants` in
   `backend/online/allocation_writer.go`) asks the same question about the
   same identifier and has the same blind spot: it reads the participant of a
   seat and asks the removal tables about it, so a seat that the sanitation
   replaced with the anonymized sentinel passes its check. The friend surface
   closes the hole for its own writes, and the foundation worker owns the
   writer. The friend surface keeps its own copy of the sentinel constant
   until the shared removal vocabulary owns one; the two must name the same
   string.
10. The pending read of a rematch offer retires a dead offer, so a read path
    writes once for a dead offer and never again. The write touches only a row
    that names nobody any more, and it takes no account scope lock, so it
    cannot invert the order of the removal.
